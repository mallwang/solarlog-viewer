Hover state — moving the mouse onto an "i" icon (here: "Monatsertrag in €") reveals its tooltip above the icon; moving away hides it again. Icons near the panel's right edge (Ist, Vermiedenes CO2) anchor their tooltip from the right instead of centering, so it never gets clipped by the panel boundary (FR-007).
Keyboard-focus state — tabbing to an icon reveals the same tooltip via :focus-visible, satisfying FR-008: the explanation isn't hover-only. Shown here on "Monatsertrag in €".
Touch / no-hover state — on a touch-only device the info icons are not rendered at all (see the panel above with the viewport switched to Mobile): there's nothing a tap could usefully do with one, so rather than shipping an inert icon the feature removes it, keeping the stats panel exactly as clean as it is today. Detection is via (hover: hover) and (pointer: fine), not screen width, so a touchscreen laptop with a trackpad still gets the icon and hover behavior (see spec Assumptions).

Fixed constraints: icon is a real focusable <button> element (not a decorative span) so keyboard tabbing reaches it for free; tooltip text is sourced from a single central label→explanation map (FR-006) so the month/year views can reuse the same "Soll"/"Ist"/"Vermiedenes CO2" entries; both the hover/focus tooltip and the icon's very presence are gated behind (hover: hover) and (pointer: fine) — on a touch-only device the icon isn't rendered at all, never a screen-width breakpoint.

Out of scope for this mockup: the exact tooltip positioning library/algorithm (illustrative CSS only — flip-on-edge is real behavior, but "smart" auto-placement for every possible icon position is a plan-time concern); the day/year/total/welcome views' stats panels, which reuse the identical .stats-panel/.summary-table markup shown here (see stats-panel.js) and are not re-mocked per view; touch devices with an attached mouse mid-session (assumption documents the pointer-capability approach, not a live toggle demo).
