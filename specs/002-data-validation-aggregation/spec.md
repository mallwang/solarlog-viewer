# Feature Specification: Data Validation & Aggregation

**Feature Branch**: `002-data-validation-aggregation`

**Created**: 2026-07-30

**Status**: Done

**Input**: User description: "I would like to add some validation and aggregation scripts and agentic skills. The basis for all calculations are the daily files "minYYMMDD.js", which result in the daysall.js, days_hist.js, months.js and years.js. ## User Scenarios & Testing _(mandatory)_

### User Story 1 — Detect Data Gaps in Daily Minute Files (Priority: P1)

The plant owner wants to find out which calendar days are missing a `minYYMMDD.js` file — either because the SolarLog device failed to log, or because a file was never transferred — so that the scope of data loss is known before any repair is attempted.

**Why this priority**: Missing daily files are the root cause of the aggregation mismatches. Identifying gaps is the prerequisite for every other validation or repair action.

**Independent Test**: Run the gap-detection script against the full archive and confirm it produces a human-readable report listing every missing date between the earliest and latest known file.

**Acceptance Scenarios**:

1. **Given** the archive of `min*.js` files, **When** the gap-detection script runs, **Then** it outputs a list of all calendar dates in the range [earliest file date … today] for which no `minYYMMDD.js` exists.
2. **Given** no files are missing, **When** the script runs, **Then** it outputs "No gaps detected" and exits with code 0.
3. **Given** a gap of multiple consecutive days, **When** the script runs, **Then** the gap is reported as a date range (e.g., "2015-08-10 – 2015-08-14: 5 days missing") rather than five individual lines.
4. **Given** the script is run with a `--since YYYY-MM-DD` flag, **When** it runs, **Then** only gaps on or after that date are reported.

### User Story 2 — Validate Plausibility of Daily Energy Totals (Priority: P1)

The plant owner wants to verify that the daily energy total recorded in `days_hist.js` matches what can be derived from summing the 5-minute records in the corresponding `minYYMMDD.js` file, and to flag days where the totals diverge beyond a tolerance.

**Why this priority**: Mismatches between minute-file totals and `days_hist.js` daily totals are the known symptom. Finding which specific days are inconsistent is required before any repair. `daysall.js` is device-generated and is not the repair target.

**Independent Test**: Run the plausibility script against a known-mismatched day and confirm the script correctly identifies and reports the discrepancy.

**Acceptance Scenarios**:

1. **Given** a day whose `minYYMMDD.js` sums to a different value than `days_hist.js` records, **When** the validation script runs, **Then** it reports the date, the minute-derived total, the `days_hist.js` total, and the absolute and percentage difference per inverter.
2. **Given** a day where the totals match within a configurable tolerance (default ±1 Wh), **When** the script runs, **Then** that day is not flagged.
3. **Given** a day for which no `minYYMMDD.js` exists, **When** the script runs, **Then** that day is skipped or reported as "no source data" rather than causing a script error.
4. **Given** the script is run with `--output json`, **When** it completes, **Then** a machine-readable JSON file is produced alongside the human-readable report.

### User Story 3 — Fill Gaps and Regenerate Aggregated Files (Priority: P2)

After gaps and mismatches are identified, the plant owner wants to fill missing entries in `days_hist.js`, `months.js`, and `years.js` so the viewer displays consistent data.

**Why this priority**: Gap-filling is the repair action that closes the loop after validation. Without it, the viewer continues to show incorrect or missing totals.

**Aggregation rules** (these are invariants, not implementation choices):

- `days_hist.js` is the sole target for historical daily per-inverter totals. `daysall.js` and any other `days*.js` files are **not modified** by these scripts.
- A missing entry in `days_hist.js` is filled using a **two-pass strategy**:
  1. **First**: look for the date in any existing `days*.js` file (e.g., `days.js`, `daysall.js`) that already contains a matching record.
  2. **Second** (only if pass 1 yields nothing): aggregate from the `minYYMMDD.js` file for that date.
- `months.js` and `years.js` entries are **always** aggregated directly from `minYYMMDD.js` files — never derived from `days_hist.js` or any other aggregated file. This ensures monthly and yearly totals remain independent of any `days*.js` inaccuracy.
- Each aggregation script is scoped to a **single calendar month or year** so it can be invoked precisely for the affected period without processing the entire archive.

**Independent Test**: Run the `days_hist.js` gap-fill script on a month where a day is missing in `days_hist.js` but present in `days.js`; confirm it takes the value from `days.js` (pass 1) and not from the minute file.

**Acceptance Scenarios**:

1. **Given** `days_hist.js` is missing an entry for a date that exists in `days.js`, **When** the gap-fill script runs for that month, **Then** it copies the value from `days.js` (pass 1) and inserts the correct entry into `days_hist.js`.
2. **Given** `days_hist.js` is missing an entry for a date where only a `minYYMMDD.js` file exists, **When** the gap-fill script runs, **Then** it aggregates from the minute file (pass 2) and inserts the result into `days_hist.js`.
3. **Given** a target month for `months.js` regeneration, **When** the script runs, **Then** it reads only `min*.js` files for that month and writes the monthly total per inverter — even if `days_hist.js` entries are present.
4. **Given** a target year for `years.js` regeneration, **When** the script runs, **Then** it reads only `min*.js` files for that year and writes the annual total per inverter.
5. **Given** the script is run in `--dry-run` mode, **When** it completes, **Then** no files are written; computed values are printed to stdout for review.
6. **Given** the target output already contains values for the affected period, **When** the script runs without `--force`, **Then** it prompts the user for confirmation before overwriting.

### User Story 4 — Agentic Gap-Fill Skills (Priority: P2)

A developer working on this project wants Claude Code slash-command skills that can detect and fill gaps in `days_hist.js`, `months.js`, or `years.js` for a **single specified month or year**, presenting a structured summary of what was found and what was changed.

**Why this priority**: Scoping each skill invocation to one month or year keeps context small and avoids loading thousands of files at once, making the workflow practical in a Claude Code session.

**Independent Test**: Invoke the `days_hist.js` gap-fill skill for a specific month; confirm it reports gaps found, sources used (pass 1 vs pass 2), and entries written.

**Acceptance Scenarios**:

1. **Given** the skill is invoked for a specific month (e.g., `2026-05`), **When** it runs, **Then** it checks only `days_hist.js` entries for that month, reports any gaps, and fills them following the two-pass strategy (days file first, minute file second).
2. **Given** the skill is invoked for a specific year and target file `months.js`, **When** it runs, **Then** it aggregates monthly totals for that year from `min*.js` files only and writes the missing or corrected entries.
3. **Given** the skill is invoked for a specific year and target file `years.js`, **When** it runs, **Then** it aggregates the annual total from `min*.js` files only and writes the missing or corrected entry.
4. **Given** the skill finds no gaps for the specified period, **When** it completes, **Then** it reports "No gaps found for [period] — nothing written."
5. **Given** the skill finds gaps it cannot fill (no source data in any `days*.js` file and no `min*.js` file for that date), **When** it completes, **Then** it reports the unfillable dates and suggests the user check for missing FTP-transferred files.

### Edge Cases

- What happens when the archive contains a `min*.js` file whose date is in the future (clock drift on the SolarLog device)?
- How does the plausibility check handle partial days — files logged on the first or last day of operation that cover fewer than 24 hours?
- What if a `minYYMMDD.js` file is present but empty or malformed (truncated FTP transfer)?
- What happens if `daysall.js` or `months.js` are missing entirely (first-time setup)?
- How does month/year boundary aggregation handle days that span midnight in the device's local time?

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: The gap-detection script MUST accept the archive directory as an argument and scan all `minYYMMDD.js` files within it.
- **FR-002**: The gap-detection script MUST report each missing date between the earliest and latest known file, grouping consecutive missing dates into ranges.
- **FR-003**: The gap-detection script MUST support a `--since YYYY-MM-DD` flag to limit reporting to a specific date range.
- **FR-004**: The plausibility-validation script MUST parse each `minYYMMDD.js` file and compute the total energy (sum of 5-minute power readings) for that day per inverter.
- **FR-005**: The plausibility-validation script MUST compare computed totals against the corresponding per-inverter entries in `days_hist.js` and report discrepancies exceeding a configurable tolerance (default: ±1 Wh). `daysall.js` is not a validation target.
- **FR-006**: The plausibility-validation script MUST support `--output json` to emit a machine-readable report.
- **FR-007**: Gap-fill scripts MUST produce output that is byte-for-byte format-compatible with SolarLog-generated files (same variable names and assignment patterns: `da[dx++]=`, `mo[mx++]=`, `ye[yx++]=`).
- **FR-008**: Gap-fill scripts MUST support `--dry-run` mode that prints computed values without writing files.
- **FR-009**: Gap-fill scripts MUST require explicit confirmation (interactive prompt or `--force` flag) before modifying existing output files.
- **FR-010**: The `days_hist.js` gap-fill script MUST implement the two-pass strategy: attempt to source missing values from any existing `days*.js` file first; fall back to aggregating from `minYYMMDD.js` only when no `days*.js` record exists for that date. `daysall.js` itself is never modified.
- **FR-011**: `months.js` and `years.js` gap-fill scripts MUST source data exclusively from `minYYMMDD.js` files — not from `days_hist.js` or any other aggregated file.
- **FR-012**: Each gap-fill script MUST accept a single month (`YYYY-MM`) or year (`YYYY`) argument and process only that period, not the entire archive.
- **FR-013**: All scripts MUST be ESM JavaScript (`scripts/*.js`) with JSDoc on every exported function and a co-located `*.test.js` file using `node:test`. Tests MUST be written before the implementation (TDD).
- **FR-014**: All scripts MUST pass `npx eslint` with zero errors before being considered complete.
- **FR-015**: Each agentic gap-fill skill MUST be defined as a `.claude/skills/*.md` file following the project's existing skill pattern (see `backfill-min-day` skill), scoped to a single month or year argument.
- **FR-016**: The agentic skills MUST invoke the corresponding gap-fill script and present a structured summary (gaps found, source used per gap, entries written) without requiring the user to know individual script flags.

### Key Entities

- **MinuteFile** (`minYYMMDD.js`): One file per calendar day; contains 5-minute interval records with timestamp, per-inverter power (W), and cumulative counter (Wh). Source of truth for all calculations.
- **DaysAll** (`daysall.js`): Flat list of all daily energy totals (date | total Wh). Derived from MinuteFiles. Format: `dal[dxl++]="DD.MM.YY|<Wh>"`.
- **DaysHist** (`days_hist.js` and per-year variants): Daily totals split by inverter. Format: `da[dx++]="DD.MM.YY|<WR1_Wh>;<WR1_feed>|<WR2_Wh>;<WR2_feed>"`.
- **Months** (`months.js`): Monthly energy totals per inverter. Format: `mo[mx++]="01.MM.YY|<WR1_Wh>|<WR2_Wh>"`.
- **Years** (`years.js`): Annual energy totals per inverter. Format: `ye[yx++]="01.01.YY|<WR1_Wh>|<WR2_Wh>"`.
- **ValidationReport**: Output of gap detection + plausibility check; contains gap list, mismatch list, and summary statistics. Produced in both human-readable and JSON form.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: The gap-detection script processes all 7,000+ daily files and produces a gap report in under 10 seconds on a standard development machine.
- **SC-002**: The plausibility-validation script identifies 100% of days where the minute-derived total differs from the aggregated total by more than the configured tolerance.
- **SC-003**: The aggregation script regenerates all output files with values that match the sum of available minute data to within ±1 Wh per day.
- **SC-004**: After running the aggregation script, the existing SolarLog viewer correctly renders all five visualization modes without modification to any viewer code.
- **SC-005**: All scripts achieve zero ESLint errors and all unit tests pass, with each test file containing at least one assertion per logical branch.
- **SC-006**: The agentic skill can be invoked from a Claude Code session and completes the full validation pipeline without requiring the user to look up script names or flags.

## Assumptions

- `minYYMMDD.js` files are the ultimate source of truth. `days_hist.js`, `months.js`, and `years.js` are derived and can be repaired. `daysall.js` and other `days*.js` files are device-generated and are never modified by these scripts; they may be used as read-only data sources.
- The target file for all historical per-inverter daily totals is `days_hist.js`. No other `days*.js` file is written to.
- `months.js` and `years.js` values are computed exclusively from `minYYMMDD.js` files to ensure they are not contaminated by any errors in `days_hist.js`.
- The two-pass gap-fill for `days_hist.js` (days file first, minute file second) ensures that device-recorded values take precedence over re-aggregated estimates wherever available.
- The tolerance for plausibility mismatch defaults to ±1 Wh; users may override this via a `--tolerance` flag.
- The 5-minute power readings in `minYYMMDD.js` are in watts (W); daily totals are in watt-hours (Wh), computed by integrating the 5-minute power readings (power × 5/60).
- The SolarLog device uses local German time (CET/CEST); day boundaries in filenames follow the device clock.
- Scripts run in Node.js 22+ (the project's current runtime); no polyfills for older environments are needed.
- The existing `backfill-min-day` skill serves as the reference pattern for the agentic skills implementation.
- Repaired output files will be manually deployed by the plant owner via FTP or file copy; no automated deployment pipeline is in scope.
- The `days_hist.js` per-year split files (`days_hist_06.js` through `days_hist_YY.js`) follow the same format as `days_hist.js` but are scoped to a single calendar year; the gap-fill script handles both the main file and split files.
