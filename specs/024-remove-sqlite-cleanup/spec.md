# Feature Specification: Remove SQLite Data Store

**Feature Branch**: `024-remove-sqlite-cleanup`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "Hi, I would like to remove all the sqlite database resources we earlier thought of in another spec. This idea is not valid anymore and a hollistic cleanup is needed. The only way the data is kept is as JavaScript files, e.g. the min*.js files. This is a hard dependency based on the SolarLog data handling."

## User Scenarios & Testing _(mandatory)_

### User Story 1 - Maintainer no longer sees a dead data-storage path (Priority: P1)

A maintainer working in the codebase (or an AI coding agent following project docs) should never be pointed toward a SQLite-based sync/storage workflow, since it was an abandoned idea and the project's real, hard-dependency data source is the SolarLog device's generated JavaScript files (`min*.js` and related aggregate files). Any command, script, spec, or doc reference to SQLite is misleading and wastes time if followed.

**Why this priority**: This is the core motivation — stale instructions actively cause wrong work (e.g., running a sync command that talks to a database that isn't part of the real architecture).

**Independent Test**: Search the repository for SQLite references (scripts, `package.json` commands, docs, specs marked active) and confirm none remain outside of historical/archived records; running `npm run` shows no SQLite-related command.

**Acceptance Scenarios**:

1. **Given** the repository after cleanup, **When** a maintainer runs `npm run` (or inspects `package.json` scripts), **Then** no script references SQLite or a `sync:sqlite`-style command.
2. **Given** the repository after cleanup, **When** a maintainer searches project documentation (`README.md`, `CLAUDE.md`) for "sqlite", **Then** no results are found.
3. **Given** the repository after cleanup, **When** a maintainer looks at `scripts/`, **Then** no SQLite-specific script or its test file exists.

---

### User Story 2 - No leftover SQLite artifacts on disk (Priority: P2)

Any SQLite database file(s) generated by the abandoned workflow should be removed from the repository (or, if such files are user data rather than repo-tracked, from the working tree) so they don't get mistaken for a live data source or accidentally referenced again.

**Why this priority**: Leftover binary artifacts are lower-impact than misleading instructions (P1) but still create confusion and repo bloat.

**Independent Test**: Confirm no `*.sqlite*` / `*.db` files remain in the repository after cleanup, and that `.gitignore` no longer carries SQLite-specific entries that imply the workflow is still supported.

**Acceptance Scenarios**:

1. **Given** the repository after cleanup, **When** a maintainer searches the working tree for `*.sqlite*`/`*.db` files, **Then** none are found.
2. **Given** the repository after cleanup, **When** a maintainer inspects `.gitignore`, **Then** it contains no SQLite-specific ignore rules that reference the removed workflow.

---

### User Story 3 - Retired spec is clearly marked, not silently deleted (Priority: P3)

The original SQLite-meter-sync spec (`specs/004-sqlite-meter-sync/`) documents a design decision that was tried and abandoned. Rather than erasing that history, it should be clearly marked as superseded/abandoned so future readers understand the SQLite idea was considered and rejected, and why.

**Why this priority**: Preserves institutional knowledge without leaving ambiguous, actionable-looking instructions lying around — lowest priority since it's about historical record-keeping, not active correctness.

**Independent Test**: Open `specs/004-sqlite-meter-sync/spec.md` and confirm it carries a clear "Superseded/Abandoned" status marker and a pointer to this cleanup spec.

**Acceptance Scenarios**:

1. **Given** `specs/004-sqlite-meter-sync/spec.md`, **When** a maintainer opens it, **Then** its status clearly states the feature was abandoned and superseded, with a reference to this spec.

---

### Edge Cases

- What happens to any generated SQLite database file currently sitting in the working tree (not committed to git)? It is deleted as part of cleanup since it has no further purpose.
- What if other, unrelated scripts import or depend on the SQLite sync module (e.g., shared utilities)? Cleanup must confirm no other script depends on the removed module before deleting it, and update/remove any such dependents.
- What if a downstream doc (e.g., a plan or task file in another spec) references the SQLite sync command? Those references should be identified and corrected or annotated as stale, at least in actively-referenced project docs (`README.md`, `CLAUDE.md`); references inside other retired/completed spec folders are left as historical record unless they cause active confusion.

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: The project MUST NOT provide any script, CLI command, or `package.json` entry that syncs data into or out of a SQLite database.
- **FR-002**: The project MUST NOT retain SQLite-specific source files (sync scripts and their tests) in `scripts/`.
- **FR-003**: The project MUST NOT retain generated SQLite database files (`*.sqlite*`, `*.db`) anywhere in the working tree.
- **FR-004**: Active project documentation (`README.md`, `CLAUDE.md`, and any other currently-referenced onboarding/instruction docs) MUST NOT describe or instruct use of a SQLite-based workflow.
- **FR-005**: The `.gitignore` file MUST NOT contain entries that exist solely to ignore SQLite artifacts from the removed workflow.
- **FR-006**: The original SQLite-meter-sync specification (`specs/004-sqlite-meter-sync/`) MUST be marked with a clear "abandoned/superseded" status rather than deleted, preserving the historical record of the decision.
- **FR-007**: The project's documented data-handling model MUST clearly state that generated JavaScript files (`min*.js` and related SolarLog-exported aggregate files) are the sole, hard-dependency data source — no database layer exists or is planned.
- **FR-008**: Cleanup MUST verify no other active script or module imports/depends on the removed SQLite sync code before removal, and MUST update or remove any such dependents.

### Key Entities

- **SQLite sync script**: The retired script (and its test) responsible for syncing SolarLog data into a SQLite database; to be removed.
- **SQLite database file**: The generated `.sqlite3` artifact previously produced by the sync script; to be removed from the working tree.
- **JS min data files**: The `min*.js` (and related day/month/year aggregate) files exported by the SolarLog device — the confirmed, sole data source going forward; unaffected by this cleanup other than clarified documentation.
- **Retired spec record**: The `specs/004-sqlite-meter-sync/` folder — kept but re-labeled as abandoned/superseded, not deleted.

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: A repository-wide search for "sqlite" across active scripts, `package.json`, and top-level docs (`README.md`, `CLAUDE.md`) returns zero matches after cleanup.
- **SC-002**: Zero SQLite database files exist in the working tree after cleanup.
- **SC-003**: A new contributor reading `README.md`/`CLAUDE.md` can correctly identify `min*.js`-style JavaScript files as the only data source, with no competing or contradictory database references.
- **SC-004**: The abandoned spec (`specs/004-sqlite-meter-sync/`) is discoverable and its status is unambiguous within 10 seconds of opening the file (status line at the top).

## Assumptions

- The SQLite sync workflow (`scripts/sync-sqlite.js`, `scripts/sync-sqlite.test.js`, the `sync:sqlite` npm script, and the `data/solarlog.sqlite3` file) was experimental/never adopted in production and has no external consumers depending on it — it is safe to remove entirely rather than deprecate gradually.
- "Holistic cleanup" means: source scripts, npm scripts, generated artifacts, `.gitignore` entries, and active documentation — not rewriting git history or deleting the original spec folder.
- No other in-repo script or module has a hard runtime dependency on `scripts/sync-sqlite.js`; this will be verified during implementation (FR-008) and this spec does not assume it needs a redesign of other scripts.
- The `min*.js` JavaScript files (produced by the SolarLog device's own export mechanism) remain, as already established elsewhere in the project, the single hard-dependency data source — this spec only clarifies/reinforces that in docs, it does not change how those files are read or processed.
